# Review of the code, 2026-11-11

Written by an agent for the user and for the next agent, at the user's request: the relations in the code (the fragile ones too), the points that can be cleaned, and what the direction of the game asks of today's structure.

It is a photo of one night. When a point here is solved or decided, delete it from this file or move the decision to `AGENTS.md`; do not let it rot.

**How to read each claim.** Every point says what it rests on:

- **read**: seen in the code as it is at this commit.
- **measured**: a number from a run on the agent's machine (Node, the real definitions unless said otherwise). The scripts are `tests/agent/benchmark-*.js` or a few lines that are easy to repeat.
- **opinion**: the agent's judgement. The user decides.

Game values are named, not copied, like in `AGENTS.md`. The numbers below are measurements, not values of the game.

---

## 1. The shape of the code

Three layers, and the direction of every arrow matters:

```
src/data.js      what the game is (frozen)      read by the rules, never written
src/sim.js       the rules                      reads data, changes the state, knows no screen
src/history.js   snaps and the cross-check      copies the state, calls step
src/input.js, render.js, main.js, chamber-2.js  the shell: reads the state, never changes it (only main calls step)
```

What goes into a step: `(state, input, blueprint)`. What a run is: `seed + blueprint + the list of inputs`. Everything else is derived. This is the strongest property of the project and most of the points below are about keeping it true as the game grows.

Inside `step`, the order is: the input is copied in; every actor moves (the avatar with its own collision against objects, right there); every actor's cells are written; the Dummies collide (objects, avatar, each other). **read**

## 3. Relations that nothing guards

Each one: what it is, where it lives, how it breaks, and the cheapest guard. Ordered by how likely they are to bite.

### 3.1 The first dash and `safeRadius` — **read**

The `safeRadius` of a layer promises that the first dash cannot hit an object. The promise depends on the distance of a dash, which comes from the dash speed of the Booster, the top speed and `overspeedDecay`. Only a comment ties them. A stronger Booster breaks the promise silently.

Also: the safe circle is measured from the origin of the world, not from where the avatar starts. They coincide today. A stage that starts elsewhere would have rocks on the avatar.

*Guard:* a test on the definitions, in the style of 101, that computes the dash distance of the starter blueprint and compares. Or drop the promise and state it as a guess.

### 3.2 Crossing a thing in one frame — **read**

The comment on `dashSpeed` says it must stay below the avatar radius plus the smallest object radius. Nothing checks it. The real rule is wider: for any two things, the speed at which they close in must be below the sum of their radii. With Dummies it is the dash speed plus the speed of the Dummy against the avatar radius plus the smallest Dummy radius. Today it holds with room.

This is the rule that projectiles will break first (small and fast).

*Guard:* a test on the definitions for every pair of recipes that can meet. When projectiles come, the rule must become a mechanism (a swept test), not a limit on numbers.

### 3.3 The version of the definitions is raised by hand — **read**

`DEFINITIONS_VERSION` must go up whenever a definition changes, and nothing fails if it does not. Nothing refuses a state made with another version either. A snap replayed against other definitions diverges, and the cross-check would report it as "not deterministic", which is the wrong diagnosis.

*Guard:* a test that keeps a fingerprint of `src/data.js` (comments aside) next to the version, so changing one without the other fails. And `stateFromSnap` (or the cross-check) refusing a snap of another version, with a clear message. Both are small.

### 3.4 The salts of the hash have no list — **read**

Every question asked of the seed has a salt, so the answers do not follow each other. The salts are numbers written where they are used: the objects use the first six (plus a hundred times the place of the layer), the Dummies use a few in the tens, the turn of a Dummy one more, the birth two more. Two were retired with the old placement. Nothing stops a new roll from reusing one, and the bug would be invisible: two things correlated that should not be.

Two consequences already live:

- **The place of a layer in the list is part of the world.** A new layer placed before an existing one changes every object of the layers after it, for every seed. New layers go at the end. (Which layer wins an overlap is decided by the size of the square, not by the order, so the order is free for this.)
- Objects have room for about a hundred kinds of roll per layer before two layers would meet.

*Guard:* one table of named salts in `src/sim.js`, and a test that they are all different. Cheap, and it turns a convention into a fact.

### 3.5 What is checked when the definitions load, and what is not — **read**

Checked: weights whole, sizes, health ranges, bounce, the speed of the Dummy, the layers. **Not checked:** `safeRadius` (a missing one would put objects on the start without any error), the count of Dummies, the acceleration and deceleration of the avatar, the specs of the parts (a negative speed, a spec name with a typo adds nothing and says nothing), that the starter blueprint has parts that exist (it fails later, at `createRun`, which is fine), the `initial` of each actor.

The typo is the one to worry about: `sumSpec` treats an unknown spec as zero, so `dashspeed` instead of `dashSpeed` silently removes the dash. With a hundred parts, this will happen.

*Guard:* a list of the spec names the rules read, and a refusal of any other name in a part.

### 3.6 The order of the list of actors is law — **read**

The result of a step depends on the order of `state.actors`: who is pushed first changes where everyone ends. This is fine and deterministic, and the grid tests protect it. But it carries hidden assumptions:

- The avatar moves before the Dummies only because it is first in the list. The wrap of a Dummy is measured from the avatar's position, so if the avatar were not first, some Dummies would wrap around where it was a frame ago. The code finds the avatar by id; the tests assume it is `actors[0]`.
- When actors die, removing one must not reorder the others.
- When a stage summons actors, their place in the list decides their collisions. Appended at the end is the natural rule; it should be said.
- The Dummy's identity for the seed is `wander.index`, not its place in the list. That is right (a death does not change anyone's future turns), and it should stay.

*Guard:* state it in `AGENTS.md` (done tonight in the guidelines) and add the avatar-first assertion when stages arrive.

### 3.7 The window is not quite an invariant — **read**

A Dummy wraps when it moves. After that it can be pushed, and the avatar can be pushed too, so at the end of a step a Dummy can sit a few pixels outside the window until the next step. Harmless, but "every actor is inside the window" is false by a push, and a strict check would fail. If the invariant is ever enforced, it needs either a tolerance or a wrap after the collisions.

### 3.8 A contact that is broken and made again is a new hit — **measured**

A hit needs a new contact. A contact stays alive only while the two keep overlapping frame after frame. A pair that is pushed to just touching, separates for a frame and meets again counts as new: a new hit, and a new turn for the Dummy.

Measured with the avatar standing still among the Dummies for a minute: 35 new contacts with the avatar, of which 2 were the same Dummy again within half a second, the closest 15 frames apart. So it happens, rarely, and never frame after frame. With chasing enemies (which keep coming at the avatar instead of turning away) it will be much more frequent, because they will bounce off the push and return.

*This is a rule of the game the user should own:* how soon can the same enemy hurt again by contact? Today the answer is an accident of the geometry. A minimum time between hits of the same pair would make it a decision.

### 3.9 Where things are identified by having a field — **read**

The rules tell kinds apart by which fields exist: a thing with `square` is an object, a thing with `move` is an actor, a thing with `wander` is a Dummy, the avatar is the one with a certain id. It works with two actors and two objects. It breaks the day an object moves (a rolling boulder), an actor comes from the seed, or a second kind of enemy has no `wander`.

### 3.10 The keys of the contacts are built in four places — **read**

`"avatar|rock layer:x,y"`, `"dummy|rock layer:x,y"`, `"dummy|avatar"`, `"dummy|dummy"`: each written where it is used, and the order of the two names differs (the avatar comes first against an object and second against a Dummy). Test 90 parses them. The damage trace will want to ask "who touched whom" and will have to parse them too.

*Guard:* one function that makes the key of a pair, with a fixed order.

### 3.11 The table of colors — **read**

`render.js` picks the color of an object from a table by type. A type that is not in the table is drawn with no color set, which in a canvas means the last color used: wrong, and silent. The project's style is to fail loudly.

### 3.12 Chamber 2 prints the whole state — **read**

Both SIMULATION CHECK and DATA print a state as indented JSON. Since the Dummies, that is a thousand actors, tens of thousands of lines. The purpose of Chamber 2 is text the user can paste; it has stopped being pasteable. What to print instead (the avatar and a count? the first few actors?) is for the user to say.

## 4. Tensions in the structure

These are not bugs. They are places where two good rules pull in different directions, and where the next features will force a choice. Better to choose than to have it chosen by the first feature that arrives.

### 4.1 Values calculated once and values calculated every frame — **read; decided by the user on 2026-11-11**

This point said that two rules of the user pulled apart ("read from the object" and "do not store what can be computed"). The second was never his: an agent wrote it. **His rule:** every final value is calculated again every frame and written into the actor; the code reads the actor; the state is rich and small (see `AGENTS.md`, "State, definitions, blueprint and rules").

What was wrong in the code against that rule, and is being fixed: some values were calculated only when the actor was made (radius, weight, bounce, acceleration, the numbers of the dash, the maximum health, the speed of a Dummy) and others every frame without being stored (the top speed of the avatar, the dash speed, the defense). Anything that changed a value during a run would have reached some rules and not others.

What stays open after the fix: what the calculation starts from when something changes an actor for a while (an aura, a transformation). The final functions start from the recipe, the parts and what the seed rolled; an effect will be one more term in them.

### 4.2 Three things are mixed in the collision of a Dummy — **read, then opinion**

`touchDummy` does physics (push apart), damage (who hurts whom) and behavior (the Dummy turns). And there are two routines for "an actor meets an object": the avatar's (`collideWithObjects`: bounce, sliding, the minimum impact decides the bounce) and the Dummy's (no bounce at all, no change of velocity, a turn).

Rules that follow from this and that nobody decided:

- A Shroom bounces the avatar and not a Dummy.
- A Dummy never changes velocity because of a contact; the avatar does against objects and does not against actors.
- The avatar pressing into a Dummy keeps its full velocity and is pushed back every frame: it plows, at a speed set by the weights.

The user's rule is that all actors are the same box. The second kind of enemy (one that chases) will have to choose a routine, and neither fits.

**Opinion.** Before the second enemy: one routine for any two things that touch (contact, push by weight, bounce, velocity), one place that says who hurts (it exists: `bodySlamHurts`), and the reaction of the actor as its own thing ("on a new contact, the Dummy turns" is the Dummy's brain, not physics). The grid tests compare whole states, so they will say at once if the refactor changed a result. It is a day of work with a good net under it; after three kinds of enemies it would be a week without one.

### 4.3 "Dummy" where "actor" is meant — **read**

`collideDummies`, the index of the grid, the wrap and the movement in `step` all select `actor.wander`. The grid does not serve actors, it serves Dummies. The names say so honestly, which is good; the day there is a second actor that moves, each of these must become "every actor that moves", and the Dummy's walk becomes one behavior among others.

### 4.4 The avatar as a special case — **read**

Five places ask "is this the avatar?": who has parts, whose weight comes from the blueprint, whose speed has a weight penalty, who can hurt, who can dash on input. One id, one avatar. It is right for today. It rules out, without anyone having decided, anything that shares the avatar's nature: a second player, a clone or a summon that inherits the build, an enemy mecha made of parts (which would be a natural boss for this game). If any of those is wanted, the question becomes "does this actor have a blueprint?" and not "is this the avatar?".

### 4.5 The push moves positions, not velocities — **read**

The push by weight separates two actors by moving them. Nobody's velocity changes. So there is no knock-back: the frame after a push, each one walks again exactly as it wanted. The user's idea of a dash that opens space when surrounded cannot come from this push alone: a dash through a crowd would shove each enemy by the overlap of one frame, and they would close in again at once. Opening space needs the enemies to *keep* moving away for a moment: a velocity given to them (an impulse), or a short stun. It is a formula of the game, so it is the user's.

### 4.6 The history costs as much as the game — **measured**

A snap is a full copy of the state through JSON. With the thousand Dummies a snap is about 420 KB, a copy takes about as long as a step, and the hundred snaps kept are 40 MB or more. Every frame of Chamber 1 pays it. With no Dummies it is nothing.

It is fine for a test chamber. It is the first thing that will not scale to a ten-minute map with a crowd, and the history is also what the pause, the frame-by-frame and the machine learning stand on. Options, for later: keep inputs for every frame and a snap every N frames (a replay rebuilds the frames between); or snap only on demand (pause). The run is `seed + blueprint + inputs`, so the inputs alone already hold everything.

## 5. Costs measured

Node, the agent's machine, a thousand Dummies, the avatar still. Chromium is several times faster on the same code (a step of the real game took about 2 ms there). Compare the lines, not the absolute numbers.

| | ms per step |
|---|---|
| The real game | about 9 |
| The same with no objects on the ground | about 5 |
| With no Dummies | about 0.02 |
| One copy of the state (a snap) | about 4 |

- **Finding the objects near each Dummy is a little under half of a step.** Each search builds every object it looks at from the recipe, with two copies through JSON, and throws it away. A layer of huge objects doubles it again (see `tests/agent/README.md`, "Cost of the layers"). The cheapest fix, when it hurts: roll the position and the radius of a square first, build the object only if it can touch. The next: remember the objects of a square for the length of a step (a cache, not state).
- **The rest is the grid and the pairs.** It scales with how crowded the cells are, not with the area.
- The contacts of the last frame are searched as a list for every contact. With about seventy contacts it is nothing. With thousands of touching pairs (a real crowd pressed on the avatar) it grows with the square; a set built once per step fixes it.

## 6. Where the game is going, and what it asks of today

For each thing that is coming: what is ready, what has to be decided first, and the trap. All of this is **opinion** built on what is **read**; none of it is a decision.

### Stages: actors summoned by frame

*Ready:* the birth rule (off the screen, inside the window, no search), reproducible from the seed and a number; the wrap; the grid for any size.

*Decide first:* the shape of the array (the user asked not to have it invented). What a line needs to say, at least: the frame, which actor, how many. And what the number of each born actor is: the birth place and the Dummy's turns come from the seed and that number, so it must be unique in the whole run and must not depend on how many actors are alive. "The n-th actor ever born in this run" is the simplest that works; it needs a counter in the state.

*Trap:* computing "what is born in this frame" by walking the array from the start every frame. The array is sorted by frame, so the state only needs to remember how far it has read. And: an actor born relative to where the avatar is *at that frame*, not at the origin.

### Death

*Ready:* health stops at zero; identities are ids, not places in the list.

*Decide first:* what a death leaves (nothing? a drop for the Magnet?), whether the body still collides in the frame it dies, and what the avatar's death does to the run.

*Trap:* removing from the list while a loop walks it, and anything that keeps the place in the list of a dead actor (the grid index is rebuilt every step, so it is safe; the contacts of the last frame can name a dead actor, which is harmless). Dead actors should leave in one place, at the end of the step, in order.

### Weapons and projectiles

This is the largest piece still missing, and it touches everything.

*Decide first:* is a projectile an actor? By "everything is the same box" it would be: a radius, a position, a velocity, a weight (so it can hit by the same formula, or not), a life. Then it is born, collides through the grid, hurts by a rule, and dies. The thing the box does not have yet is **who owns it** (so it does not hurt its shooter, and so the audit can say which weapon did the damage) and **who it can hurt**. `bodySlamHurts` answers "who hurts whom" with "the avatar is one side"; with weapons the question becomes one of sides (the avatar's side, the enemies' side), and the same function is the place for it.

*Trap:* tunneling (3.2), and the count. A thousand enemies and a few hundred projectiles is where the cost of the grid and of the history (4.6) will be felt. Projectiles against objects is the search of section 5 again, once per projectile per frame.

The Radar (who can be targeted) is a query "the actors within a radius", which the grid can answer; today the grid only answers "who shares my cells", so that query is new.

### Shield, and everything with a now and a max

*Ready:* the mold `{ now, max }`, and one function through which every damage to an actor passes (`applyDamage`). The shield goes there: it takes first, health takes the rest.

*Decide first:* how it comes back (the user said it is not defined). Whatever the rule, it has memory (frames since the last hit), so it is state.

### Buffs and effects

See 4.1: this is the decision that shapes it. Besides that, the state will need a list of active effects with their remaining time. `crushes` is the first effect that exists: a boolean that an aura will switch. The user was clear that the time belongs to the buff and the boolean to the actor. If two auras can overlap, a boolean cannot say "one of the two ended"; it needs to be computed from the active effects ("is any effect that gives crushing alive?"), which is again 4.1.

### The damage trace and the audit page

The second axis of the concept, and nothing of it exists yet.

*State today:* damage is computed by `damageOf`, which returns one number, and applied in four call sites. The terms (the weight, the impact, the attack, the defense, whether the minimum was applied) exist for an instant inside the function and are lost.

**Opinion: build the trace before the second source of damage.** One function that resolves a hit and returns a record of it: who, whom, when, the terms in the order they were applied, the result. The crush is its own kind of record. Then the body slam is the first user, and weapons, the shield, buffs each add terms to a structure that exists. Done after weapons, it means rewriting each source. It is also what makes the user able to *check* the formulas that are his, which today he can only do by reading test tables.

Where the records live: they are not state (they do not change the future), so they should not be in the snaps. A list beside the history, filled by `step` through an argument, keeps the state small and the replay able to rebuild them.

### The library, and parts made by the seed

*Today:* one flat object; a type is a short id; actors and objects share one space of names (an actor and an object with the same id would silently be the actor).

*What moves when the library comes:* the `type` of everything in the state becomes an address; the keys of contacts and of hurt objects contain types and layer names; the color table; every test that patches the text of `src/data.js` (there are dozens, all guarded now by test 111, so they will fail loudly, which is the good way to find them).

*Trap:* doing it late. Each new kind of content written flat is one more thing to move. But doing it now, with four entries, would be designing it without knowing what skills and weapons look like. **Opinion:** move when the first weapon or skill is about to be written, not before and not after.

Parts by seed bring owned items with stored rolls: the blueprint stops being a list of ids and becomes a list of instances. Everything that takes a blueprint already takes it as an argument, so the change stays inside the blueprint functions. That choice (the blueprint as an input of the run) was a good one.

### Pause and frame by frame

The history exists and has no buttons. See 4.6 for its cost. The agreed order of work in `AGENTS.md` puts this second, after the user plays; it is still the cheapest thing that would let him see what happens in a collision, which is what every formula discussion needs.

### Machine learning

*What it needs from the simulation:* run without a browser (it does: the tests already do), run much faster than real time (it does not depend on the clock: test 113), reset to a state, step with an action, read an observation and a reward.

**Opinion on the language question** (the user thinks the ML work will be in Python): do not port the rules to Python. Two implementations of a deterministic simulation drift, and the whole value here is that there is one truth. Drive the JavaScript rules from Python: a small Node program that reads actions and writes states, one line of JSON each way. The tests show the rules load in Node with nothing but two files. The cost per step of crossing the process is small next to a step with a crowd.

What ML will want that does not exist: counters in the state (damage dealt, damage taken, kills), because a reward is a difference between two frames; and a compact observation, because a state with a thousand actors as JSON is not something to feed a network.

### The feel of the game

None of tonight's rules was played by the user: the push by weight, the birth off the screen, damage only with the avatar. The order of work in `AGENTS.md` said to stop adding rules until inertia, dash, collision and body slam had been felt; four rules were added on top since. They are tested for *what they do*, not for *whether they are good*. The numbers behind them are mostly guesses and say so.

## 8. Cleaning left undone, and why

- **The `blueprint` argument that some final functions do not use** (`finalRadius`, `finalAcceleration`, `finalDeceleration`, `finalBounce`). It is there so every final function has the same shape. The user said he was not sure. It is tied to 4.1: if final functions become the only way to read a value, the uniform shape is right and the argument stays. Left as it is.
- **`collideWithObjects` and `touchDummy` take the same things in a different order.** Cosmetic; it goes away with 4.2.
- **The test file is one file of 2400 lines.** It works, and one file is easy for the user to run and paste. Splitting it by subject would help an agent find things; it is not urgent.
- **Chamber 2's output** (3.12): needs the user's word on what to print.
- **The color table** (3.11): failing loudly on an unknown type is a small change of behavior, so it was not done under "nothing new".
