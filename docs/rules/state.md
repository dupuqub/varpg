# State, definitions and the run history

## In short

- The same initial state, blueprint and inputs always give the same run (docs/rules/state.md).
- One step per frame shown, at a fixed rate: no step is skipped and nothing unseen is calculated, so a slow machine plays in slow motion (docs/rules/state.md).
- Buttons and keys pause, play and walk one frame back or forward through the saved frames; play on a past frame, even one before the death, discards what came after and goes on with new inputs (docs/rules/state.md).
- The state is a single JSON object, a photo of the game now: what can change in a run is state, what never changes is a definition, and what the player chose before the run is the blueprint (docs/rules/state.md).
- The definitions are frozen and never change in a run; the blueprint is an input of the run, kept outside the saved frames (docs/rules/state.md).
- What the rules calculate is written into its actor, the dynamic values again every frame (docs/rules/state.md).
- The state carries the version of the definitions, and a saved frame of another version is refused (docs/rules/state.md).
- The history keeps the last saved frames (snaps) and the input that made each, in two aligned lists, plus the blueprint (docs/rules/state.md).
- The cross-check replays the saved inputs from the oldest snap and reports the first difference; it proves the run repeats, not that the rules are right (docs/rules/state.md).
- Going back loads a copy of a snap, so playing on never rewrites the history (docs/rules/state.md).

## Simulation

- **Deterministic:** the same initial state, blueprint and inputs produce an identical run. One of the goals is to reproduce runs for machine learning.
- **60 steps per second.** All game values are based on 60 fps.
- Physics is calculated once per frame: **one step per displayed frame**. Steps are never skipped and frames that are not shown are not calculated ("calculate and show, always"). If the machine cannot keep 60 fps, the game runs in slow motion.
- **The game state is a single JSON object.**
- **Frame debug (the user, 2026-11-12; built):** the game views of Chambers 1 and 2 have three buttons in the top bar: `||` / a triangle (pause and play), `<<` (one frame back) and `>>` (one frame forward), plus a status text (`PAUSED`, `FRAME n` of the game, and `HISTORY i/m`: the place of the shown snap among the saved ones, 1 being the oldest). Back and forward pause the game and walk through the saved snaps (`stateFromSnap`, the last `HISTORY_SIZE`, so two seconds of walking back); forward on the newest frame plays one new step with the input of that moment. **Play on a past frame discards everything after it (`discardAfter`) and goes on from there with new inputs** (confirmed by the user on 2026-11-14, issue 42: it holds for as long as the history is a debugger, and in the finished game a death will not be undone). A click gives the focus back (`blur`), or the Space key (the dash) would press the button again. **Keys for the same buttons (the user, 2026-11-12):** `P` pauses and plays (it ignores key repeat, so holding it does not flicker); `,` (or `<`) steps back, `;` or `.` (or `>`) steps forward, read by what the key types so they work on any layout; the user named `;` for forward, and `.` was added in case his key with `>` is that one; holding a key repeats the step. **A fourth button, `[ ]`, toggles fullscreen** (the user, 2026-11-12): it is hidden where the browser cannot do it (an iPhone), and on a phone entering fullscreen also asks for the landscape orientation (the agent's addition, because the game needs it; refused silently where the browser does not allow it). The logic is in `src/main.js` (it touches the page), so it has no Node test. **Past the death (issue 42):** the buttons stay after the avatar dies and back and forward walk the saved snaps; play on a snap from before the death undoes it (see "Destruction" under "Actor" (docs/rules/actor.md); tests 222 to 225).

## State, definitions, blueprint and rules

**The state is rich and small at the same time (the user's rule, 2026-11-11).** Everything the rules calculate is stored in the actor it belongs to (what is dynamic is calculated again every frame, what is static once, at the start of the run; see "Actor" (docs/rules/actor.md)), the rest of the code reads it from the actor, and the snap keeps what was true in that frame ("I do not know how to work another way; leaving things out of the state is not optimal"). And the state stays small: nothing goes in that does not say something about the game now. His image: a boat, and the work is not to fall off either side, neither bloating the state with information nor taking essential pieces out of it. The state is a **photo** of how the game is now, not of what is done in it. Rule of thumb: if it can change during a run, it is state; if it never changes, it is a definition; if the player chose it before the run, it is the blueprint.

- **Definitions (the "db", to be called the library, see "The library"):** what the game *is*. They never change during a run. They live in `src/data.js`, a plain object `DEFINITIONS` that is deep-frozen, loaded by `<script>` so `index.html` still opens directly. There are exactly six things in it today: three actors (`DEFINITIONS.actors`: the avatar, created by hand with its **initial state**, which `finalizeObject` only copies, so no number about how an actor is born is hidden in code; and the Dummy and the Biter, made by the seed from ranges) and three objects (`DEFINITIONS.objects`: the rock, the Shroom and the Branch, created only by the seed, from ranges; test 73). A thing points to its definition by id (`type`), and `definitionOf(thing)` returns it. **Cleanliness rule (the user's, strong; the goal, which the code does not fully meet yet):** every value in the definitions is defined and used by something; what is not used is deleted and comes back when something needs it. No placeholder: a value of a non-avatar thing comes from the seed (a range), and a value of the avatar comes from its definition or its parts. Open exceptions, which the user has not decided yet and which stay in the definitions until he does: the `name` of every actor and of every object (`avatar`, `dummy`, `biter`, `rock`, `shroom`, `branch`), which no rule and no drawing reads; and the tag `vermin` of the Biter, which no attack targets or ignores, so nothing reads it. The `name` of a part is used: `src/render.js` draws the weapon line with it.
- **State:** only what changes: positions, velocities, health of the avatar (`{ now, max }`), dash charges, the frame, the seed, the map (which spawn events it plays, issue 61), the objects that were hurt, the grid settings, the version of the definitions.
- **Blueprint (the user's name, chosen on 2026-11-10):** the structure of the mecha the player chose for the run: for now the list of mecha parts. The word **build** is kept for the ordinary meaning (the process of building something, and the genre word for a combination of skills and parts), so the code never uses it as a name for this list. The skill tree (the processor) is a separate thing and has no name in the code yet. It is an **input** of the run, like the seed and the inputs, not a state: it does not evolve, and it is not inside the snaps. Only the avatar has a blueprint; other actors read their definition directly. `createRun(id)` returns `{ id, blueprint }` with a copy of the starter blueprint and refuses an invalid one (`assertValidBlueprint`). The blueprint is the **third argument of `step`** and of every `final...` function that needs it, and `createHistory(state, blueprint)` keeps it for the replay. Nothing is pre-resolved (the user, 2026-11-09).
- **Effects: recipe versus result.** Take a torso that gives armor per enemy within a radius. What it does (the recipe) is in the definitions, in the part. Whether the player uses it is in the blueprint. How much it gives *now*, being dynamic, is calculated every frame by a pure function (like `finalSpeed`) from the recipe, the blueprint and the state, **and written into the actor** (see the rule above), so anything that changes during a run reaches every rule that reads the value.
- Keep an eye on lists of active effects, which are the fields that grow the most.
- **Rules (code):** `step` and the `final...` functions. The order of the phases is written in `step`, is the same in every run, and is not stored anywhere.
- The state carries the **version of the definitions** it was made with (`state.definitionsVersion`, from `DEFINITIONS_VERSION`, raised by hand on any change). `stateFromSnap` refuses a snap of another version, and a test keeps a fingerprint of the data next to the version.

## Run history (two logs)

Agreed with the user. Implemented in `src/history.js` and recorded by the loop of Chambers 1 and 2 (the pause, back and forward buttons walk through it; no automatic cross-check yet; from the browser console, `crossCheck(runHistory)` runs it).

- **Vocabulary:** a **snap** is a saved copy of the state at one frame (the user's word). "State" is the live one.
- Each snap carries `run` and `frame`, so a snap exported to disk can be identified. The rules never read `state.run`.
- The game keeps the last `HISTORY_SIZE` snaps and inputs, in two lists where index 0 is the oldest. The lists are **aligned**: same index = same frame, and `inputs[i]` is the input of the step that produced `snaps[i]`. The first snap has no input. Snaps and inputs are saved as copies. The history also keeps the blueprint of the run (tests 20 and 21).
- **Cross-check** (`crossCheck(history)`): take the oldest snap, apply the saved inputs with `step`, and compare each result with the snap of the same frame. It returns `null` or the first difference (`{ frame, path, expected, actual }`). A difference means something is not deterministic (tests 22 to 24). Planned: run it continuously.
- It proves **consistency**, not **correctness**: a wrong rule replays equally wrong. Correctness is the job of the tests and of the damage audit.
- No hashes: the comparison is state against state, and the states stay readable JSON.
- **Going back while paused (built, `src/main.js`: `stepBack`, `stepForward`, `playGame`):** the user can walk back through the saved frames. Pressing play on a past frame discards the snaps **and inputs** after it (`discardAfter`, test 25; confirmed by the user on 2026-11-14, issue 42, for as long as the history is a debugger). Going back must load a **copy** (`stateFromSnap`), because `step` changes the state in place.
